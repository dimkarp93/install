# Требования к go-программам для установки через install.sh

Программа должна удовлетворять следующим требованиям, чтобы её можно было установить и обновить через `install.sh`.

## Обязательные требования

### 1. Публикация на GitHub с семантическим тегом

Релизы публикуются через GitHub Releases. Тег каждого релиза — строго `vMAJOR.MINOR.PATCH` (например, `v1.2.3`).

### 2. Версия хранится в `versions.txt`

В корне репозитория — файл `versions.txt` с голым semver без `v` (например, `0.4.0`). Версия встраивается в бинарь через `ldflags` при сборке.

### 3. Имя репозитория совпадает с именем бинаря

Последний сегмент имени репозитория (`owner/NAME`) должен совпадать с именем исполняемого файла. Установщик по умолчанию выводит имя бинаря из имени репозитория: `dimkarp93/envs` → бинарь `envs`.

Если имена расходятся (например, репо `mvpy-env`, а бинарь `envs`), пользователь обязан передавать имя бинаря явно: `github_install.sh dimkarp93/mvpy-env envs`. Это неудобно, поэтому **рекомендуется называть репозиторий так же, как бинарь**.

### 4. Имена ассетов

К релизу прикреплены архивы для всех поддерживаемых платформ:

```
<имя>-linux-amd64.tar.gz
<имя>-linux-arm64.tar.gz
<имя>-darwin-amd64.tar.gz
<имя>-darwin-arm64.tar.gz
```

Здесь `<имя>` — имя бинаря (= имя репозитория, см. п. 3).

### 5. Файл SHA256SUMS

К тому же релизу прикреплён файл `SHA256SUMS` — вывод команды `sha256sum *.tar.gz`. Установщик проверяет целостность архива по этому файлу перед распаковкой.

### 6. Структура архива

Исполняемый файл `<имя>` находится в одном из двух мест внутри архива:

- в корне: `<имя>`
- в каталоге с именем платформы: `<имя>-<os>-<arch>/<имя>`

Других обязательных файлов в архиве нет.

### 7. Флаг `--version`

Бинарь при запуске с флагом `--version` (или `-v`) выводит в stdout строку с голым semver:

```
0.4.0
```

Не добавлять префикс `v`, не добавлять лишнего текста — только версия на отдельной строке.

## Рекомендации

### Статическая сборка

Собирать с `CGO_ENABLED=0` и `-trimpath -ldflags="-s -w -X main.version=<ver>"`. Это гарантирует, что бинарь работает на любом Linux/macOS без зависимости от системных библиотек.

### Идемпотентный CI-релиз

Workflow должен проверять существование тега и пропускать сборку, если тег уже есть. Это делает повторный push в `master` безопасным.

### Переиспользуемый workflow

Используйте шаблон `workflows/release.yml` из этого репозитория — он уже реализует все конвенции: сборку для 4 платформ, генерацию `SHA256SUMS`, идемпотентность.
