# Требования к программам для установки

Чтобы программу можно было установить и обновить через установщики этого репозитория —
как из GitHub Releases (`github_install.sh`), так и локально из рабочей копии
(`local_install.sh`) — она должна удовлетворять описанным ниже требованиям.

Программа может быть написана на любом языке: установщикам важен лишь готовый исполняемый
файл и соблюдение конвенций об именах, архивах и версиях.

## Общие требования

### 1. Имя бинаря

По умолчанию имя исполняемого файла совпадает с именем каталога репозитория (оно же — имя
репозитория на GitHub, последний сегмент `owner/NAME`). Установщики выводят имя бинаря из
имени каталога: каталог `<имя>` → бинарь `<имя>`.

Если имя бинаря отличается от имени каталога, в корне репозитория должен лежать файл
`bin.txt` — одна строка с именем бинаря:

```
<имя-бинаря>
```

Установщики и release-workflow берут имя бинаря из `bin.txt`, если он есть, иначе — из
имени каталога/репозитория. **Рекомендуется** называть репозиторий так же, как бинарь —
тогда `bin.txt` не нужен.

### 2. Имена ассетов

К релизу прикреплены архивы для всех поддерживаемых платформ:

```
<имя>-linux-amd64.tar.gz
<имя>-linux-arm64.tar.gz
<имя>-darwin-amd64.tar.gz
<имя>-darwin-arm64.tar.gz
```

Здесь `<имя>` — имя бинаря (см. п. 1).

### 3. Файл SHA256SUMS

К тому же релизу прикреплён файл `SHA256SUMS` — вывод команды `sha256sum *.tar.gz`.
Установщик проверяет целостность архива по этому файлу перед распаковкой.

### 4. Структура архива

Исполняемый файл `<имя>` находится в одном из двух мест внутри архива:

- в корне: `<имя>`
- в каталоге с именем платформы: `<имя>-<os>-<arch>/<имя>`

Других обязательных файлов в архиве нет.

### 5. Локальная сборка (для `local_install.sh`)

В репозитории есть таргет `just build` (в `Justfile`) **или** `make build` (в `Makefile`),
который кладёт исполняемый файл `<имя>` (имя бинаря, см. п. 1) в **корень репозитория**.
`local_install.sh` использует этот таргет для установки программы локально, до публикации
GitHub Release.

```
<корень-репозитория>/<имя>   ← бинарь должен оказаться здесь после just/make build
```

## Версии

### Семантический тег релиза

Релизы публикуются через GitHub Releases. Тег каждого релиза — строго `vMAJOR.MINOR.PATCH`
(например, `v1.2.3`).

### Версия хранится в `versions.txt`

В корне репозитория — файл `versions.txt` с голым semver без `v` (например, `0.4.0`).
Версия встраивается в бинарь при сборке (например, через `ldflags`).

### Флаг `--version`

Бинарь при запуске с флагом `--version` (или `-v`) выводит в stdout строку с голым semver:

```
0.4.0
```

Не добавлять префикс `v`, не добавлять лишнего текста — только версия на отдельной строке.

### Рецепты bump-патч/минор/мажор

Для удобного поднятия версии репозиторий предоставляет в `Justfile` (или `Makefile`)
рецепты `bump-patch`, `bump-minor`, `bump-major`. Каждый из них увеличивает соответствующую
компоненту semver в `versions.txt` (обнуляя младшие компоненты) — по аналогии с
release-тулингом (см. стиль `Justfile` инструмента `jira`):

- `bump-patch`: `1.2.3` → `1.2.4`
- `bump-minor`: `1.2.3` → `1.3.0`
- `bump-major`: `1.2.3` → `2.0.0`

Пример рецептов для `Justfile`:

```just
bump-patch:
    #!/usr/bin/env sh
    set -eu
    v=$(tr -d '[:space:]' < versions.txt)
    IFS=. read -r MAJ MIN PAT <<EOF
    $v
    EOF
    printf '%s.%s.%s\n' "$MAJ" "$MIN" "$((PAT + 1))" > versions.txt
    cat versions.txt

bump-minor:
    #!/usr/bin/env sh
    set -eu
    v=$(tr -d '[:space:]' < versions.txt)
    IFS=. read -r MAJ MIN PAT <<EOF
    $v
    EOF
    printf '%s.%s.0\n' "$MAJ" "$((MIN + 1))" > versions.txt
    cat versions.txt

bump-major:
    #!/usr/bin/env sh
    set -eu
    v=$(tr -d '[:space:]' < versions.txt)
    IFS=. read -r MAJ MIN PAT <<EOF
    $v
    EOF
    printf '%s.0.0\n' "$((MAJ + 1))" > versions.txt
    cat versions.txt
```

Выпуск новой версии: `just bump-patch` (или minor/major) → закоммитить `versions.txt` →
смержить в `main`/`master`. Workflow создаст тег и релиз.

## Рекомендации

### Статическая сборка

Собирать без зависимости от системных библиотек (для Go — `CGO_ENABLED=0` и
`-trimpath -ldflags="-s -w -X main.version=<ver>"`). Это гарантирует, что бинарь работает
на любом Linux/macOS без внешних зависимостей.

### Идемпотентный CI-релиз

Workflow должен проверять существование тега и пропускать сборку, если тег уже есть. Это
делает повторный push в `master` безопасным.

### Переиспользуемый workflow

Используйте шаблон `workflows/release.yml` из этого репозитория — он уже реализует все
конвенции: вычисление имени бинаря (из `bin.txt` или имени репозитория), сборку для
4 платформ, генерацию `SHA256SUMS`, идемпотентность.
